# tdd/ —— 测试与需求映射目录

本目录回答两个问题：**测了什么**、**每条测试对应哪条需求**。它是测试存在性的依据——没有对应需求的测试是冗余，没有测试对应的需求是缺口。

## 放什么

- `mapping.md`：测试清单与需求映射表。每个测试一行：测试名（`tests/*.rs` 中的函数名）→ 覆盖的需求（来源是 `docs/sdd/` 的具体条目）→ 验证要点。
- 新增子系统时，在该文件追加一节（如 LLM 子网关一节），或拆出同构的子文件并在 `mapping.md` 中索引。

## 不放什么

- 测试代码本体（放 `tests/*.rs`）
- 接口契约（放 `../sdd/interfaces.md`，那是规格）
- TDD 循环的**过程记录**（红 → 绿 → 重构的失败形态，放 `../cycles.md`）
- 需求复述与范围（放 `../sdd/overview.md`）

## 与其他目录的分工

| 位置 | 回答 |
|---|---|
| `../sdd/` | 系统应该长什么样（规格，先于代码） |
| 本目录 | 测试覆盖了哪些规格条目（映射） |
| `../cycles.md` | 测试先行的循环怎么走过来的（过程） |
| `../../README.md` | 用户怎么用（操作） |

## 维护规则

- **先改规格再加测试**：新增测试前，`sdd/interfaces.md`（或对应子系统规格）里必须已有它要钉的条目；映射表同步登记。
- 测试删除或改名时同步改映射表；`cargo test` 的函数名与映射表必须一直对得上。
