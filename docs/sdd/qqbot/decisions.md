# 设计决策（QQ Bot 子网关）

> **SDD 第 5 步**：ADR 记录。只解释前 4 步中**真实出现过**的选择，每条追得到具体子文档。

| # | 决策 | 背景（为什么需要选） | 备选与后果 |
|---|---|---|---|
| Q1 | **内嵌模块**而非独立子网关进程 | 与 LLM 子网关同一仓库、同一 axum/tokio/reqwest 栈；换 token 与事件投递能直接复用 `state.client` 连接池 | 备选：独立二进制经 `routes.toml` 挂 `/qqbot`。后果：多一跳 HTTP、机器人配置与进程级 client 无法共享；采用内嵌则 `/qqbot` 前缀被进程保留（见 Q5） |
| Q2 | **显式 app_id 路径段** `/qqbot/{app_id}/...` | 一个网关可同时接入多个机器人；入站路径必须无歧义地选出凭证。与 `/llm/{protocol}` 同构的「显式段」原则 | 备选：按 Host / 自定义头选机器人。后果：SDK 的 base_url 多写一段（`http://gw:8000/qqbot/{app_id}`），但换来确定性；多机器人共存不需要客户端侧任何额外配置 |
| Q3 | **以响应体 `access_token` 存在判成功**，不看 HTTP 状态 | 参考文档明确「换 token 接口 HTTP 恒 200，业务错误码在响应体 `code` 里」——按 HTTP 状态判会把 `100007`（appid 无效）错当成功 | 备选：按 HTTP 状态 + body `code` 双判。后果：多余——平台文档说死 200；单判 `access_token` 存在已经覆盖「成功/失败/畸形响应」三类。`TokenFetchFailed` 统一映射 502 |
| Q4 | **`expires_in` 自定义反序列化两种都收** | 官方文档规范写 number，返回示例写成字符串 `"7200"`——按单一形态解析会直接让整个换token 流程挂掉 | 备选：只按字符串解析再用 `serde_json::Number` 兜底。后果：`Option<u64>` + 自定义 visitor 更直白；解析失败丢弃该字段并按 7200 兜底（平台约定值），错误不致命 |
| Q5 | **`/qqbot` 前缀保留**，nest 优先于 routes fallback | 内嵌模块与 `routes.toml` 前缀转发的路由决策必须有一个赢家（与 ADR-L5 同构） | 后果：运维在 `routes.toml` 挂 `/qqbot` 前缀不会生效（被 nest 截流）。已写入 overview.md 的非功能约束；测试钉住「`/qqbot` nest 与路由表共存」的语义 |
| Q6 | **同 token 字符串不回写 + 刷新冷静期 30s** | 平台规则：token 有效期 7200s，临近过期 60s 内才能换到新 token——窗口外刷新**返回同一个 token 字符串**。若无脑回写 `expires_at`，会把旧 token 的有效期错误重置成 7200s；且换 token 接口本身有 100001 限流 | 备选：每次 `remaining ≤ 300s` 都刷。后果：临近过期的每一秒都在打平台接口，触发 100001；冷静期 + 同 token 不回写两个机制叠加后，`remaining > 300s` 走无锁快路径，`≤ 300s` 每机器人每 30s 至多一次单飞刷新 |
| Q7 | **只做 op 13 签名应答，不做入站事件验签** | 本地参考文档只给出**验证请求**的签名算法（己方私钥签名）与 `X-Bot-Appid` 头；平台推送事件时的签名头与验签公钥未提供 | 备选：盲造一个验签头格式。后果：无规格就是无规格——编出来的校验要么永远过要么永远挂。当前只校验 `X-Bot-Appid` 与路径 app_id 一致（401）。风险 R4 记录该缺口与「怎么验证」 |
| Q8 | **禁用的机器人在转发路径 503、回调路径 404** | 两个通道的「禁用」语义不同：转发是「明确告诉你不可用」（与路由 disabled 的 503 同构）；回调是「这个地址不再存在」——平台侧探测地址可达性时 503 仍是「存在」，404 才是「摘除」 | 备选：回调也返 503。后果：平台重试逻辑可能持续把回调打到禁用机器人上；404 让平台侧的地址注册自然失效 |
| Q9 | **一个机器人一条 WS 连接，不做分片编排** | `shard` 字段透传给 Identify 即可满足单机器人需求；分片编排（按 guild_id 哈希分桶、多连接协调）是平台侧 SDK 的职责，网关把它做成配置面会引入跨连接 seq 同步问题 | 后果：单个高频机器人无法靠网关水平扩展分片；需要时配多个 app_id 或在平台侧解决。`shard = [0,1]` 是默认形态，字段原样透传不解释 |
| Q10 | **网关不校验 `event_source` 与平台权限组合** | webhook 形态要平台侧登记回调地址、websocket 形态要平台侧开权限——这是**平台配置**，网关侧无法得知 | 后果：配错形态时由平台兜底：websocket 无权限 → op 9 Invalid Session 或关闭码 4014（supervisor 按关闭码分流的不可重试分支停止并记 `last_error`）；webhook 未登记 → 平台根本不推送。`EventSource` 接受任意值（不变式 Q0） |
| Q11 | **不做客户端鉴权；`app_secret` 明文落盘** | top-gateway 的定位是「子网关自己做业务鉴权」；QQ Bot 子网关沿袭该定位（与 ADR-L11 同构） | 后果：`/qqbot/*` 对任何能连到端口的人开放、`app_secret` 明文出现在管理 API 与 `bots.toml`。**部署侧义务**：绑定回环 / 前置反代 / 设 `GATEWAY_ADMIN_KEY`。风险 R5 记录 |
| Q12 | **`api_base` / `ws_url` / `event_url` 逐机器人覆盖** | 正式 / 沙箱由 `sandbox` 一键切换已能覆盖多数场景；但指向自建 mock、内网反代或测试订阅器时需要逐机器人 escape hatch | 备选：只留全局环境变量。后果：测试一个机器人必须重启整个网关；逐机器人覆盖让「一个网关里混跑正式与沙箱机器人」成为可能，`resolve_*()` 是纯函数、覆盖值优先 |
| Q13 | **ACK 先于投递，投递失败不重试**（at-most-once） | 平台 webhook 推送有超时约束——先做签名应答 / op 12 ACK 再投递订阅者，投递慢或挂会拖垮平台侧的推送窗口 | 备选：同步投递成功再 ACK。后果：订阅者一慢，整个平台推送链路被拖住；且平台侧 webhook 无重投约定，WebSocket 断线期间的事件靠 Resume 补发属平台行为。失败只计 `record_error` + 日志，不向平台暴露（风险 R6） |
