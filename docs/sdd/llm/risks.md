# 风险登记（LLM 子网关）

> **SDD 第 6 步**：评估前 5 步定下来的系统。每条风险必须有「怎么验证」。

| # | 风险 | 影响 | 缓解 | 怎么验证 |
|---|---|---|---|---|
| R1 | **TPM 记账是 best-effort**：无 `usage` 字段（模型/供应商不返回）、流被中断、或 tail 缓冲（64 KiB）没覆盖到 usage 时记 0，TPM 计量偏低 | 配额比实际宽松，窗口末端可能轻微超限 | 限额配置留余量；`extract_tokens` 对无 usage 情况显式记 0 条而非静默跳过（`record_tokens(0)`），使请求次数仍精确 | 单测 + 集成测试 `llm_usage_missing_records_zero_tokens`；`llm_counts_tokens_from_streaming_final_chunk` 覆盖 SSE 末尾 usage |
| R2 | **在途请求令牌未预留**：派遣时只扣 RPM，token 要等响应回来才入账 | 高并发 + 大 TPM 限额时窗口内实际占用被低估 | 可接受（LLM 响应延迟通常 << 60s 窗口）；后续可加预估预扣 | 集成测试：同一供应商并发发若干请求后查 `/__admin/llm/quota` 的 `tpm.used` 与已完成响应累计一致 |
| R3 | **加权随机的短样本波动**：权重 0.9 / 0.1 的两个供应商，10 次请求里小权重者可能一次都没选到（的概率约 35%） | 分布式流量在分钟级自然均衡，单测样本不可作为分布断言 | 测试只钉确定性边界（权重为 0 即排除、耗尽即 429、全满前不误拒） | `llm_exhausted_provider_falls_back_to_remaining`、`llm_rpm_exhaustion_returns_429` |
| R4 | **错误体非原生协议格式**：OpenAI/Anthropic SDK 收到 429/502 时走通用错误分支，拿不到原生 `error.type` 等字段 | SDK 侧的错误处理代码要按状态码而非错误体结构写 | house 格式 `{"error":{"code","message"}}` 信息足够 SDK 按 status code 重试；已写入 overview 非功能约束 | 集成测试断言 429/503/404 体为此格式 |
| R5 | **`/llm/*` 无客户端鉴权 + api_key 明文**（ADR-L11） | 能访问端口者可消耗全部供应商配额；`GET /__admin/llm/providers` 泄露 key | 部署侧：绑回环、前置反加鉴权、设 `GATEWAY_ADMIN_KEY`；README 环境变量表注明 | 回归测试 `llm_admin_llm_endpoints_require_admin_key`（仅钉管理端点鉴权）；残留风险记录于 ADR-L11 |
| R6 | **全满即 429，无排队**：客户端看到 429 的时间窗内所有供应商都在限额内 | 高峰期瞬时拒绝；客户端需自带退避重试 | 与需求「全满返 429」一致；429 现附 `Retry-After` 头（池级「最早可能恢复」，ADR-L24）——窗口剩余时间可算，客户端有最小退避依据而非盲等 | `llm_rpm_exhaustion_returns_429`（429 语义与消息体）+ `llm_429_response_carries_retry_after`（头存在、值 ∈ [1,60]、消息体不变）；恢复瞬间数学由 src 内单测 `quota_retry_after_*` 钉住（按本文件惯例不入 mapping.md） |
| R7 | **无失败转移**（ADR-L7）：单供应商故障 → 502 | 挂多家供应商并不能躲开单家故障 | 监控 `/__admin/llm/metrics` 的 errors 计数及时下线故障供应商（`PUT` 设 `enabled:false`）；客户端重试会落到其他仍有配额的供应商 | `llm_unreachable_provider_returns_502` |
| R8 | **`Systemone` 计量桩**（ADR-L8） | SystemOne 供应商的 TPM 计量恒为 0，按 TPM 的加权对其无效 | 桩行为有测试钉住；规格明确后只改 `usage.rs` 一个函数 | `llm_systemone_stub_forwards_without_token_counting` |
| R9 | **同一供应商被多协议误配**：`protocols` 字段决定选择池，配错协议的供应商会被打到它不支持的协议路径 | 上游返回 4xx，透传给客户端 | `ProviderInput.protocols` 必填且 `validate` 校验（非空、无重复）；`x-llm-provider` 响应头让排错时能看到实际打到哪家 | `llm_forwards_openai_path_and_bearer_key` 断言响应头；多协议池由 `llm_v1_shared_provider_serves_both_protocols` 钉住 |
| R10 | **v1 端点推断是闭表**：新端点（OpenAI/Anthropic 后续新增的 API）未登记时 `/llm/v1/{新端点}` 返回 404 | 新端点要等网关升级才能经 `/llm/v1` 访问 | 闭表即确定性（ADR-L12 拒绝前缀/模糊匹配）；逃生口是无歧义的显式协议段 `/llm/{protocol}/v1/{新端点}`，不经推断 | `llm_v1_unknown_endpoint_returns_404`（404）+ `llm_v1_ambiguous_endpoint_returns_404`（404 后显式段仍 200） |
| R11 | **组合校验存在盲区**（ADR-L15）：请求 body 无 `model` 字段 / 不是 JSON / 超出 16 MiB 缓冲上限时，app 的模型组合**无法校验** | 无 `model` 的请求（如 `POST /v1/embeddings` 变体、文件上传）可绕过组合限制打到任意协议级供应商；app 配置给出「已限制」的假象 | 文档明确「组合只覆盖带 `model` 的请求」（范围外条目）；超 16 MiB 的请求直接 413（不放进盲区）；`App.models` 只是**约束面**不是安全面——真正的隔离靠供应商分流（给不同 app 配不同供应商，而非只靠组合） | `llm_app_combo_allows_models_without_model_field`（无 model 字段的请求不因组合被拒）；`llm_oversized_body_returns_413` |
| R12 | **请求 body 缓冲的内存占用**（ADR-L14）：每个并发请求最多缓冲 16 MiB | 高并发下内存线性增长（100 并发 = 1.6 GiB 上限） | 16 MiB 是 LLM 请求体（含图片/文件 base64）的经验上限；响应方向仍流式；超限即 413 拒绝，不存在无限缓冲；网关部署规模（本地 / 小团队）下可接受 | 单测 + 集成测试 `llm_oversized_body_returns_413` 钉住上限；`llm_model_rewrite_zero_diff_passthrough` 钉住值相同时不复制不重写 |
| R13 | **代理可用性成为转发依赖**（ADR-L19）：配了 `proxy_url` 的供应商，代理故障 = 该供应商不可达 | 代理挂了照样 502（与上游不可达同语义，不新增错误形态）；可能被误判为供应商故障 | 502 消息仍含 provider id（不含代理地址——代理是部署 internals）；排错时可先 `curl` 代理确认；代理本身应做高可用（本机代理挂掉属部署侧义务）。**`validate` 的 400 闸门只在管理 API 路径上**——启动加载路径不跑校验，手工编辑 providers.toml 写入的非法代理 url 能加载、启动不失败，只在首个请求以 502「provider ... unreachable」暴露，且运维上与「代理挂了」不可区分；生产部署应通过管理 API 配置代理 | `llm_provider_proxy_routes_through_proxy`（请求确实走了代理）；`llm_unreachable_proxy_returns_502`（代理不可达 → 502）；`llm_admin_rejects_invalid_proxy_url`（配置时拦截）；`llm_file_level_proxy_url_routes_through_proxy`（文件态配置 → 实际走代理）；`llm_hand_edited_invalid_proxy_loads_but_fails_at_request_time`（手工非法代理加载通过、请求时 502） |
| R14 | **socks5 代理不被支持**：reqwest 的 `socks` feature 未启用，`socks5://...` 的 `proxy_url` 会被 `validate` 拒绝（400）；手工写入文件则能加载，请求时以传输错误 502 暴露 | 想用 socks5 代理的部署需改代码重新编译 | `rustls-tls` 已覆盖 HTTP 与 HTTPS 代理（CONNECT 隧道），覆盖主流本地代理（clash/v2ray http 端口）；如需 socks5，后续加 feature 并放宽 P14 即可，接口形态不变 | `llm_admin_rejects_invalid_proxy_url` 断言 `socks5://` 400；`llm_hand_edited_invalid_proxy_loads_but_fails_at_request_time` 断言文件态 socks5 可加载、请求 502 |
| R15 | **账本落盘有延迟窗口**（ADR-L20/L22）：`UsageLedger` 周期 flush（默认 60s），进程被 SIGKILL 强杀 / panic / 掉电时最近一个窗口的记账丢失 | 用量统计可能略低于真实消耗 | 正常 shutdown 会做末次 flush（`axum::serve` 的 graceful shutdown 之后，**先 abort 周期 flush 任务**再末次写，且 `flush_if_dirty` 经 `flush_lock` 串行化——末次写不会被周期任务的旧快照覆盖，ADR-L22）；窗口默认 60s 可经 `GATEWAY_USAGE_FLUSH_SECS` 调小（代价是更频繁的磁盘 IO）；账本是**统计面而非计费面**——配额（`QuotaTracker`）完全在内存、不受此影响，丢的是账本条目不是配额正确性 | `llm_usage_ledger_flush_writes_and_reloads`（flush 后重读 round-trip）；`llm_usage_ledger_clean_no_op`（不 dirty 时不写文件，钉住「flush 不是无脑写」）；**shutdown 顺序与 flush 串行化无确定性回归测试**（竞态时序相关，无法稳定复现）——靠代码审查与锁序推理验证，缺口登记为 R18 |
| R16 | **分桶归一是 best-effort**：openai 的 `prompt_tokens` 包含 `cached_tokens`，提取时用 `saturating_sub` 归一到 `input`；`reasoning_tokens`（`completion_tokens_details`）是 `output` 的子集，**不单列**（单列会重复计数） | 上游返回非常规字段组合（如 `prompt_tokens` 缺失但 `cached_tokens` 存在）时，桶值与「显然的」对账可能对不上；`total` 与 `extract_tokens` 的总数在不含缓存的常规响应下一致，含缓存时两接口的 input 口径不同（一个含缓存一个不含）属于**设计差异而非 bug** | 文档固定口径（P15）；`total` 与逐桶累加均为**饱和**求和（ADR-L22）——恒为四桶之和且不超过 `u64::MAX`，极端 / 恶意上游值不回绕、不 panic，账本内部永远自洽；对账需求以桶为准而非与 `extract_tokens` 对照 | 单测覆盖 openai 含缓存 / 缺字段 / anthropic 全字段 / SSE 聚合；饱和语义由单测 `usage_total_and_addition_saturate` 钉住（`u64::MAX` 桶的 total 与累加不回绕；src 内单测按本文件惯例不入 mapping.md）；集成测试 `llm_usage_records_per_app_buckets`（openai 含缓存，断言四桶与 total）与 `llm_usage_records_anthropic_cache_buckets`（anthropic 全字段） |
| R17 | **SystemOne 用量账本恒为 0**（ADR-L8/L20 同构）：`extract_usage` 与 `extract_tokens` 同为桩 | SystemOne 流量不出现在账本明细里（条目仍会创建，但全桶为 0） | 桩行为有测试钉住；规格明确后只改 `usage.rs` 一个函数（与 R8 的演进路径相同） | `llm_systemone_stub_forwards_without_token_counting`（配额侧桩，TPM 记 0）；`llm_usage_records_systemone_zero_buckets`（账本条目存在、四桶恒 0） |
| R18 | **flush 并发不变式无确定性测试**（ADR-L22 的验证缺口）：`flush_lock` 串行化所有 flush、「快照 + 清 dirty」在同一把 map 写锁内完成、shutdown 先 abort 周期 flush 任务——这三条不变式靠**代码审查与锁序推理**验证，没有能稳定复现竞态的回归测试 | 未来重构若破坏不变式（把清位移出写锁、flush 之间不再串行、或关停顺序被 revert），测试不会变红，并发丢条目 / 旧快照覆盖新数据可能静默回归 | 不变式的结构性表达留在代码里（`flush_if_dirty` 的文档注释逐条陈述不变式；`flush_lock` 字段注释；ADR-L22 记录动机与锁序推理）；R15 的丢失窗口语义由现有功能测试间接约束 | cycles.md C30 如实记录「审查驱动、测试是验证者而非驱动者」；`llm_usage_ledger_flush_writes_and_reloads` 与 `llm_usage_ledger_clean_no_op` 覆盖 flush 的**功能语义**（写盘、no-op），不覆盖其**并发语义** |
| R19 | **`Retry-After` 是 advisory**（ADR-L24）：头值是池级「最早**可能**恢复」时刻，不是保留座位的承诺 | 客户端按头值精确重试时可能再次撞 429：并发请求抢先占走刚空出的槽位（选择无排队，L6/L4/L16）；在途请求的 token 回账可能重新压满 TPM（与 R2 同源的时序缺口） | 头值取**保守下界**（数学上严格的淘汰瞬间，非经验估计）；客户端 SDK 的标准做法本就是「头值 + 抖动」退避；文档（README / interfaces 的恢复时长语义）明确其为**最小退避而非预约** | `llm_429_response_carries_retry_after`（头存在与值域）；src 内单测 `quota_retry_after_none_when_unlimited_or_not_exhausted` / `quota_retry_after_rpm_tracks_evicting_entry` / `quota_retry_after_tpm_accumulates_from_front`（恢复瞬间数学：RPM / TPM / 不限 / 未耗尽） |
