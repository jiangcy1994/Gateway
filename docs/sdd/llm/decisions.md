# 设计决策（LLM 子网关）

> **SDD 第 5 步**：ADR 记录。只解释前 4 步中**真实出现过**的选择，每条追得到具体子文档。

| # | 决策 | 背景（为什么需要选） | 备选与后果 |
|---|---|---|---|
| L1 | **内嵌模块**而非独立子网关进程 | 与 top-gateway 既是同一仓库、又共享 axum/tokio/reqwest 栈；独立进程要多一个端口与一套部署 | 备选：独立二进制经 `routes.toml` 挂载。后果：多一跳 HTTP、供应商配置无法共享进程级 client 连接池；且用户明确选择内嵌。代价：`/llm` 前缀被进程保留（见 L5） |
| L2 | **协议透传，按协议选供应商**，不做协议转换 | 三种协议的聊天接口字段差异大（messages/ system prompt/ tool 结构均不同），转换层等于重写一个适配库，错误面巨大 | 备选：入参归一化中转。后果：OpenAI 客户端打不到 Anthropic 供应商——这是范围声明而非缺陷（`overview.md` 范围外）。客户端想要跨厂商，自己用各家 SDK 各连一个协议段即可 |
| L3 | **显式协议段** `/llm/{protocol}/...`（**已被 L12 修订**，显式段保留为无歧义形态） | 入站路径必须能无歧义判定协议；纯嗅探 path（`/v1/messages` vs `/llm/v1/chat/completions`）在新协议加入时立刻脆弱 | 备选：按 path 嗅探。后果：SDK 的 base_url 多写一段（`http://gw:8000/llm/openai`），但换来确定性与可扩展性。L12 之后两种形态并存：SDK 可直接指 `http://gw:8000/llm/v1`，无歧义场景仍推荐显式段 |
| L4 | **剩余配额加权随机**，不做加权轮询 / 最小余量优先 | 「剩余配额加权」是需求原文；随机选择无状态、并发友好（无需跨请求维护游标）；加权轮询在权重随消耗动态变化时行为同样不直观 | 备选：nginx 式平滑加权轮询（确定性、无 rand 依赖）或 least-remaining 优先（会瞬间压满单一供应商）。后果：短样本下分布有随机波动，测试以「耗尽即排除」等确定性边界钉住行为 |
| L5 | **`/llm` 前缀保留**，nest 优先于 routes fallback | 内嵌模块与 `routes.toml` 前缀转发的路由决策必须有一个赢家 | 后果：运维在 `routes.toml` 挂 `/llm` 前缀不会生效（被 nest 截流）。已写入 README 与 architecture.md 的「保留前缀」声明；测试 `llm_coexists_with_route_table` 钉住共存语义 |
| L6 | **全满 429 / 无供应商 503 / 未知协议 404**，统一 house 错误体 | 三种「不可服务」原因语义不同：配额耗尽是客户端可重试的（429 语义），无供应商是配置缺失（503），协议段拼错是路径错误（404） | 备选：全部按 OpenAI/Anthropic 原生错误格式返回。后果：错误体不是原生格式，SDK 的错误解析走通用分支（风险 R4 记录）；换来的是与 top-gateway 全局错误格式一致 |
| L7 | **不做失败转移 / 重试** | 重发 LLM 请求可能产生**两次计费**（上游已接受但响应在传输中丢失时），代价高于一次 502 | 备选：仅在「连接失败、未收到任何响应头」时换供应商重试。后果：单供应商故障 → 客户端直接看到 502。可通过多挂同协议供应商 + 客户端侧重试缓解；监控看 `/__admin/llm/metrics` 的错误数（风险 R7） |
| L8 | **SystemOne 留接口桩** | SystemOne 的 usage 字段规格未定；但路由 / 选择 / 转发是协议无关的通用路径 | 桩的精确范围：`Protocol::Systemone` 全程参与（可建供应商、可路由、Bearer 鉴权、流式转发）；**仅 `extract_tokens` 恒返回 0**——即 TPM 加权对 SystemOne 供应商无效。`llm_systemone_stub_forwards_without_token_counting` 钉住此行为；规格明确后只改 `usage.rs` |
| L9 | **复用 `RouteStats`**（按供应商存独立 map），不建新指标体系 | in-flight / 延迟 / 错误计数的需求与路由指标完全同构 | 备选：为供应商写 `LlmStats`。后果：两套计数器、两套快照序列化；独立 map 防止 route id 与 provider id 碰撞串扰 |
| L10 | **`providers.toml` 独立持久化**，不塞进 `routes.toml` | 供应商是独立配置面（协议池而非前缀路由），生命周期与路由无关 | 备选：合并为一个文件。后果：`Route` / `Provider` 两个 serde 结构互相污染；独立文件还可单独做版本管理与权限控制 |
| L11 | **不做客户端鉴权；不做 api_key 脱敏** | top-gateway 的定位是「子网关自己做业务鉴权」；内嵌 LLM 网关沿袭该定位 | 后果：`/llm/*` 对任何能连到端口的人开放、`api_key` 明文出现在管理 API 与磁盘文件。**部署侧义务**：绑定回环 / 前置反代 / 设 `GATEWAY_ADMIN_KEY`。风险 R5 记录 |
| L12 | **新增 `/llm/v1/{端点}`：按端点段推断协议**（修订 L3） | OpenAI 与 Anthropic 的 SDK 都把 base_url 拼成 `{base}/v1/{端点}`；让两家 SDK 直接指 `http://gw:8000/llm/v1` 即可工作，是「适配环境」的关键一步 | 推断是**闭表**不是嗅探：只按 `v1/` 之后的首段匹配（`messages`/`complete` → anthropic；`chat`/`completions`/`responses`/`embeddings`/`moderations`/`audio`/`images`/`fine_tuning`/`batches`/`uploads`/`threads`/`assistants` → openai）。两协议共用的端点（`models`、`files`）**返回 404 并提示改用显式协议段**——不猜；未知端点同样 404。推断结果只决定选池与凭证注入，**转发路径保留客户端写法**。systemone 不参与推断（其端点空间未被映射，见 L8）。代价：新端点需登记进闭表；收益：SDK 零配置接入，且显式段仍是无歧义逃生口 |
| L13 | **`Provider.protocol` → `Provider.protocols: Vec<Protocol>`** | 部分供应商一个 base_url 同时侍奉 OpenAI 与 Anthropic 端点（共享网关型上游）；单协议字段逼着运维把同一供应商挂两遍，配额与统计也因此被对半切开 | 选择池 = 说该协议的全部启用供应商（`list_enabled_by_protocol` 改为 `contains`）；**配额、指标、tracker 仍按 provider id 存一份**——跨协议共用 RPM/TPM，与「限额是供应商级」的 P5 一致。`validate` 要求非空且无重复。旧形态单值 `protocol = "openai"` 经 serde alias 继续可读（已部署文件不启动失败），下一次原子写回即迁移为列表形态；两键都缺则解析失败（保持缺字段的大错行为） |
| L14 | **模型映射 + 请求 body 改写** | 各供应商的模型名不同（`chat-pro-2026-04` vs `chat-pro`）且费用不同；客户端写上游真名则换供应商必须改客户端，也无法做「便宜的上游优先、贵的兜底」 | provider 声明 `[[providers.models]]`（`name` 网关名 / `upstream` 上游名 / `priority`）；转发时缓冲请求 body（**上限 16 MiB，常量 `MAX_REQUEST_BODY`**）、取 `model`、按 pool_for 选供应商、`upstream` 与请求值不同则重新序列化替换 `model` 字段，**值相同时原始 bytes 零差异透传**。**空模型表 = 协议级兜底**：参与任意 model 请求的选择、不改写、effective priority = `i32::MIN`——这让现有无模型表部署（含全部历史测试）零迁移继续工作。代价：请求 body 不再流式（响应流式不受影响）；超 16 MiB 的请求直接 413（不截断转发——截断的 LLM 请求只会得到上游 400，无意义）；无 `model` 字段 / 非 JSON 的请求无法映射，按协议级路由放行（风险 R11） |
| L15 | **入站密钥即应用凭证**（修订 L11） | 不同本地 app（Claude Code / Cursor / Cherry Studio）要差异化限制可用模型；若另开一套 app 鉴权，客户端的 SDK 就要改配置——但 SDK 本来就把 `api_key` 填在 `Authorization: Bearer` / `x-api-key` 里，**入站凭证天然在请求头里** | 客户端把 app key 填在 SDK 原本填供应商 key 的位置即可；网关取 `Bearer` / `x-api-key` 的值（**常量时间比较**）识别 app。**无凭证 = 默认策略，继续放行**（修订 L11 的「不做客户端鉴权」，但不推翻其部署侧准入定位）；有凭证但未命中任何 app → **401 fail-closed**（瞎写的 key 不能换来权限）；命中但禁用 → 403；命中且 `models` 非空时，请求 model 不在组合内 → 403。组合校验只覆盖 body 内带 `model` 的请求（R11 盲区）。凭证随后仍被替换为供应商凭证（L11 的替换语义不变） |
| L16 | **优先级分层选择**（修订 L4 于有 model 时） | 「便宜的上游优先、贵的兜底」用扁平加权随机做不到（权重只反映剩余量）；严格优先级又会让低优先级供应商完全闲置 | model 存在时候选按 (provider, model) 条目的 `priority` **降序分层**；从高到低取第一个**仍存在可选用（weight>0）成员**的层，层内保持 L4 的剩余配额加权随机；层全耗尽降层；所有层全耗尽 → 429。effective priority：声明条目的 `priority`（默认 0），空模型表兜底 = `i32::MIN`（显式声明永远优先于兜底）。**无 model 请求不分层**（全员 priority 0 同层，即 L4 原语义——历史行为与测试不受影响）。选择 + RPM 记账仍在同一临界区（锁序与并发不变式不变） |
| L17 | **按供应商 timeout** | 不同供应商的网络路径差异大（国内中转 vs 官方 API），全局 30s 对慢供应商误杀、对快供应商浪费 | `Provider.timeout_secs: Option<u64>`（缺省回落 `GATEWAY_DEFAULT_TIMEOUT`，与 `Route` 的 timeout 字段同构）。504 行为不变（消息含 provider id 与实际超时秒数） |
| L18 | **`apps.toml` 独立持久化** | app 是独立配置面（凭证 → 模型组合），生命周期与供应商无关；塞进 `providers.toml` 会让两个 serde 结构互相污染 | `App` / `AppTable` / `AppsFile` 与 `Provider` 完全同构（缺文件非致命、原子写、重写丢注释）；环境变量 `GATEWAY_APPS_FILE`（默认 `apps.toml`）；管理端点 `/__admin/llm/apps*` 与 providers 端点形态一致 |
| L19 | **按供应商 HTTP 代理（`proxy_url`）** | 部署环境里部分上游只有走代理才可达（如生产环境 NVIDIA 直连被阻断，须过 `http://127.0.0.1:7890`），而同进程内其他上游可以/必须直连——全局代理设置会误伤直连供应商 | `Provider.proxy_url: Option<String>`（缺省 = 共享直连 client，行为与 0.2.1 完全一致）。转发热路径按 proxy url 从 `ClientCache` 取 reqwest client：`None` → `state.client`；`Some(url)` → 每个代理 url 一个自带连接池的 client（缓存只增不删，代理 url 变更后旧 client 自然淘汰）。**已启用的 `rustls-tls` feature 同时支持 HTTP 与 HTTPS 代理**（HTTPS 目标走 CONNECT 隧道），无需新依赖；socks5 需要 reqwest 未启用的 `socks` feature，`validate` 直接判非法（配置时 400，P14）。代理可达性仍是 502 语义（与上游不可达同列，不新增错误形态）。校验同时尝试构造 `reqwest::Proxy::all(url)`，把字符串校验漏过的非法形态拦在配置时 |
| L20 | **按日 × 应用的 token 用量账本（`UsageLedger`）** | 配额（`QuotaTracker`）只回答「这个供应商 60 秒窗口内还剩多少」，无法回答「哪个应用哪天用了多少 token、其中多少是缓存命中」——计费分摊与用量分析需要**累计、按日、按应用、分 token 类型**的口径 | 新增 `usage.rs::extract_usage`（分桶提取）与 `ledger.rs::UsageLedger`（`BTreeMap<(NaiveDate UTC, app id), Usage>` + dirty 位）。键维度**是应用而非供应商**：入站凭证（ADR-L15）天然标识应用，无凭证流量以空串哨兵入账（视图边界转回 `None`）。分桶**跨协议对齐**为 `input`/`output`/`cache_read`/`cache_write` 四桶（openai 的 `prompt_tokens` 含 cached，提取时 saturating 减去归一）。**与配额路径解耦**：`extract_tokens`（TPM 配额）逐字不变，ledger 是并行的新记账路径——互不影响、可独立演进。持久化 `usage.toml`（观测数据而非配置：无管理 API 能写它），周期 flush（默认 60s，`GATEWAY_USAGE_FLUSH_SECS`）+ shutdown 末次 flush；SIGKILL 丢失最近一个窗口（风险 R15）。查看经 `GET /__admin/llm/usage`（可选 `app`/`date`/`from`/`to` 过滤，非法日期 400） |
| L21 | **账本全量写而非增量追加** | 用量账本要持久化，但「追加日志 + compaction」给一个内嵌网关带来过大复杂度（需处理截断、损坏、滚动） | `flush_if_dirty` 每次全量序列化整个 map。账本规模 = 日数 × 应用数（量级为数百行），全量写的 IO 代价可忽略；换来的是**文件永远自洽**（无尾部截断修复逻辑）与原子替换的既有语义复用。代价：日积月累后文件缓慢增长——运维可按需归档删除（删除后下次 flush 从内存重写，不影响累计的正确性前提是内存仍持有数据；重启后历史不丢因启动加载） |
